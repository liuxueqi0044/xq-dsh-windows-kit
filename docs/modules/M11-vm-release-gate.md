# M11 Windows VM 验收与发布门禁

## 目标

在完全隔离的中英文 Windows 11 x64 VM 中验证真实用户流程，并用结构化证据决定候选是否具备上架条件。

## 环境

- 一台中文 Windows 11 x64 干净 VM；
- 一台英文 Windows 11 x64 干净 VM；
- 快照、无生产数据、无私人仓库；
- 专用临时 DeepSeek 测试账号和限额 Key，由验收者本人输入；
- 支持的 Node 22.19+ 或 24.x；
- 网络和端口故障可控模拟。

## 输入、依赖与非职责

依赖 M09 候选 ZIP、M10 自动化结果和真实 GitHub Actions 证据。M11 不修改产品实现，不使用日常主机或生产账号替代 VM，也不允许智能体生成虚构截图、签字或 PASS。

## 证据模型

每个验收项记录：ID、状态、VM 标识、OS/build/locale、产品和 DSH 版本、开始结束时间、操作命令、期望、实际结果、截图/日志摘要 hash、执行者和复核者。

状态只有 `PASS`、`FAIL`、`PENDING`、`NOT-APPLICABLE`。必需项不允许 `NOT-APPLICABLE`。证据不得包含真实 Key、一次性 Token 或会话正文。

## 验收流程

1. 干净机环境检查；
2. 从官方来源安装支持的 Node；
3. 验证供应链锁；
4. 创建专用空工作区；
5. 启动本机 Web UI；
6. 验收者本人输入临时 Key；
7. 使用 `workspace-write + ask` 完成低风险读写；
8. 验证仅 loopback 监听；
9. 重启与数据行为；
10. API、端口、网络和下载失败；
11. 简单 Skill 安装/发现/删除；
12. 预构建测试插件安装/验证/删除/回滚；
13. 诊断脱敏；
14. 最终 ZIP 扫描；
15. 证据复核和发布决定。

## 发布判定

只有以下条件全部成立才可建议 `releasable`：M01–M10 必需项 PASS；中英文 VM 必需项 PASS；GitHub main Validate 实际绿色；候选 ZIP hash 固定；供应链重新验证无漂移；两人复核发布证据；商品文案与实际能力一致。

状态修改仍是人工受控操作，不由测试脚本直接写 manifest。

## 失败模式

证据缺失、截图/日志 hash 不一致、环境不隔离、出现真实秘密、执行者与复核者相同但政策要求双人复核，均使对应门禁保持 PENDING 或 FAIL。不能通过补写说明把失败改成通过。

## 验收标准

- `VM-001`：中文和英文 Windows 11 x64 VM 均有独立证据。
- `VM-002`：干净机检查与支持 Node 安装流程通过。
- `VM-003`：锁定 DSH 从官方来源启动。
- `VM-004`：首次工作区为空且为安全窄目录。
- `VM-005`：临时 Key 只由验收者输入，证据中无明文。
- `VM-006`：受控读写任务在 `workspace-write + ask` 下通过。
- `VM-007`：3080 只监听 `127.0.0.1`，IPv4/IPv6 状态均记录。
- `VM-008`：重启后数据行为与指南一致。
- `VM-009`：API、端口、网络、下载失败均有友好结果。
- `VM-010`：测试 Skill 安装、发现、调用和删除通过。
- `VM-011`：测试插件安装、dump-config、boot、功能、删除和回滚通过。
- `VM-012`：诊断报告经人工和自动扫描均无秘密。
- `VM-013`：最终 ZIP 扫描、hash 和文件清单一致。
- `VM-014`：商品文案、售后边界和已知问题经人工复核。
- `REL-001`：main Validate 有实际绿色 run 证据。
- `REL-002`：任一必需项 PENDING/FAIL 时发布状态保持 draft/candidate。
- `REL-003`：发布决定包含执行者与复核者签字引用。
- `REL-004`：证据包中没有生产数据、私人仓库或真实凭据。
